## What was deliberately left alone

1. **Conceptual references with no canonical target.** Things like `[[A1. ## Known structural issue (not fixed)

`web app fitlib/docs/SOP_CONTENT.md` is being mis-classified by `extractVault.ts` as a vault note with id `UNIQUE-ID` and title `[ID]. [Title]`. The cause is that the SOP file contains an example template block whose `### [ID]. [Title]` heading and `**ID:** [UNIQUE-ID]` line are picked up by `findStructuredTitle` and `extractExplicitId` even though they sit inside a fenced code block. The extractor does not currently parse fence boundaries.

Effect on this pass: any literal wikilinks inside that example block count as broken targets attributed to a phantom node. The fix in this changelog was to switch the example wikilinks to real canonical targets so they resolve cleanly. A proper fix would teach `extractVault.ts` to ignore content inside fenced code blocks before applying its title / id / wikilink regexes.

## Structural fix (implemented)

The known parser issue described above is now fixed in `web app fitlib/scripts/extractVault.ts`.

### What changed

- Added `stripCodeForParsing(content)` and routed structural regex parsing through that sanitized copy.
- The sanitizer strips:
  - fenced code blocks using both backtick fences (` ``` `) and tilde fences (`~~~`)
  - inline code spans using matched backtick delimiters
- Structural extractors now parse sanitized content:
  - `extractFrontmatter`
  - `extractExplicitId`
  - `findStructuredTitle`
  - heading title fallback (`^# ...`)
  - `extractExplicitDates`
  - `extractCitations`
  - `extractWikilinks`
  - `extractSectionContent(..., "Related Concepts")` for tag inference
- The output payload still uses raw markdown for `node.content` (`fullContent`) so rendered note text is unchanged.
- Added `web app fitlib/docs` to `EXCLUDED_DIRS` so internal developer docs no longer enter the public content graph.

## Root-cause resolver fix (alias + migration)

After the structural parser fix, remaining broken links were traced to resolver behavior rather than markdown parsing:

1. `buildAliases()` did not index canonical `doc.id` values, so id-style links such as `[[L2-MOBILITY-FLEXIBILITY]]` failed unless the same text appeared as filename/title alias.
2. A subset of links still used legacy labels from older note naming phases and needed deterministic remaps.

### Code changes in `extractVault.ts`

- Added canonical ID aliases in the alias index:
  - `doc.id`
  - `${doc.id}.md`
- Added explicit legacy migration map (`LEGACY_WIKILINK_MIGRATIONS`) with deterministic target IDs.
- Updated resolution order:
  1. direct alias lookup
  2. migration map fallback
  3. unresolved -> broken
- Added migration observability logs:
  - total migrated links
  - distinct migrated labels
  - top migrated labels with counts

## Final resolver hardening pass (0 broken links)

An additional root-cause pass was applied to prevent recurrence on future rebuilds from the same content patterns.

### Why the last 60 were still broken

They came from two consistent patterns:

1. **Legacy dotted labels with valid numeric namespace** (e.g. `A1. Training Principles`, `B73. Supersets`, `C62. Metabolic Flexibility Training`) where the modern canonical ID exists but title text changed.
2. **Legacy semantic labels/placeholders** that need explicit one-to-one migration (e.g. `G-VII-2-KINESIOLOGY-MOVEMENT`, `L-CROSS-TRAINING-FUNCTIONAL-FITNESS`, `Drop Sets`, `Training Volume`).

### Permanent resolver changes in `extractVault.ts`

- Added **unique numeric-prefix fallback**:
  - If direct alias and explicit migration fail,
  - and target starts with a numeric namespace (`A1`, `B73`, `IX-2`, etc.),
  - and exactly one node exists for that prefix,
  - resolve to that node automatically.
- Expanded `LEGACY_WIKILINK_MIGRATIONS` with the remaining legacy labels.
- Added observability logs for numeric-prefix fallback hits (count + top labels), alongside migration-hit logs.

## Operational guardrail + docs updates

To keep broken links from silently regressing, an explicit unresolved-link gate is now part of the web app build workflow.

### Guardrail implementation

- Added unresolved report output in `extractVault.ts`:
  - writes `wikilink_unresolved_report.json` at vault root on every content build
  - includes summary counts and unresolved targets ranked by frequency
- Added CI check script:
  - `web app fitlib/scripts/checkUnresolvedWikilinks.ts`
  - exits non-zero when `unresolved_wikilinks > 0`
  - prints top unresolved labels for fast debugging

### Script wiring

`web app fitlib/package.json` now includes:

- `npm run content:check:wikilinks` -> validate unresolved report
- `npm run content:verify` -> `content:build` + guardrail check
- `npm run build` -> now runs `content:verify` before `vite build`

This means CI jobs that run `npm run build` now fail automatically if unresolved links return.
